# 武汉红中赖子杠 · 规则引擎

麻将程序的第一个里程碑：**把武汉规则算对**。当前是一个纯逻辑引擎，零依赖、无网络层，
可以直接单测和批量压测 —— 先把规则钉死，再往上盖房子。

> **v0.2 是一次彻底重写。** v0.1 那版实现的是「112 张 + 红中当万能牌」，那不是武汉红中赖子杠。
> 对照百度百科 / 腾讯武汉麻将大赛等来源核对后，发现 8 处结构性偏差，已全部改掉，见下方「v0.2 纠正了什么」。

> 🔴 **横溢判据是 `hOver` 不是 `overflow`**（2026-10-09 修的真实盲区）：
> `#app` 是 `overflow-y:auto`，按 CSS 规范 `overflow-x:visible` 会被降级成 `auto`
> ⇒ 内容横向出界时被 `#app` 自己吃掉，`scrollWidth` 压根不涨。只看 `overflow` 会漏掉一整类问题。
> 详见下面「`viewport-check` 的横溢判据」一节（含 `inScrollableX` 豁免规则）。

### 页面高度恒定（老吴 2026-10-03「不因牌河、按钮出现而上下拉伸」）

`viewport-check.mjs` 除了查溢出，还钉**四个元凶时刻**的几何 —— 整页高 / 牌桌高 /
我的座位下沿 / 手牌下沿，**任何一个像素都不能动**：

| 元凶 | 怎么量到的 |
|---|---|
| 响应期按钮（吃/碰/杠/胡/过 同排） | 局内驱动器在提示变成「轮到你：选择」那一刻立即取快照 |
| **胡牌提示横幅** `.win-prompt` | 单独一条路径：换种子重开，打到**能胡那一刻**停住量（常规 `fast` 局不产生响应阶段，横幅永不出现） |
| **中央倒计时转盘** `.center-dial` | 又一条单独路径：进响应期就**故意不点「过」**、停在响应期 1.2 秒，看数字有没有 N→N-1、亮/灭两态几何是否一致 |
| 结算弹窗（4 家 + 65 张牌） | 终局后等 `.st-row` 齐了再取一次快照 |
| 牌河变长 / 副露增多 | 局内每 8 步采一次样，看有没有缓慢漂移 |

> ⚠️ **以前只比「开局 vs 终局」，所以这三个元凶时刻全都没被量到** —— 报出来的「高度稳定」
> 是**不完整的**。2026-10-03 起才把它们逐个钉住。

> ❗**换种子必须用 query（`?seed=N`）而不是 hash（`#seed=N`）**（老吴 2026-10-03 踩过）：
> `Page.navigate` 到「同 URL + 不同 hash」**不会重新加载文档**（浏览器只滚锚点），
> 于是「第 2..24 个种子」其实还在同一局里空转，命中率恒为 0。
> 症状极具误导性：听牌档试 12 个种子全不中、横幅档试 24 个全不中，
> 看起来像「概率低」，实际是**种子压根没生效**。改 query 后两档都是**首次就命中**。
> `SEED_STUB` 现在读 `location.search`。

> 头像与转盘的额外断言（都在 `viewport-check` 报告里显式打出）：
> · **头像恰好 4 个且每个 ≤ 21px** —— 头像一旦大于 `.dir-badge`，上/下两家（在 grid 的
>   `auto` 行）的座位行就会变高 → `#table` 变高 → 整页抖动。这条是硬红线。
> · **结算后转盘必须已收起**（`clearResponseTimer` → `hideDial`），否则牌河上会挂一枚「0」。
> · **累计战绩分徽章 4 个**；一把未打时用 `visibility:hidden` 占位而**不是 `display:none`**，
>   保证「有分数 / 没分数」两种状态下座位行宽高完全一致。

胡牌横幅能不能命中**取决于种子**（人的出牌策略不同），所以默认 `WP_SEED=24` / `WP_TRIES=24`
（可用环境变量覆盖）。转盘档不需要「能胡」那种低概率条件，任意一次响应期就命中，默认
`DIAL_SEED=1` / `DIAL_TRIES=3`。若某档报「试了 N 个种子都没能胡，本档未覆盖」，
说明**这一档没测到横幅**，不算通过也不算失败。

> **反向对照**（`NEGATIVE_CONTROL=HEIGHT`）注回「操作条顶高整桌」的旧布局，必须检出：
> `响应期按钮 +48px`、`结算弹窗 +123/+187px`、`#app 内部溢出 24px`。
> 抓不到就说明这套检查是假绿 —— 定期跑一次给自己上保险。

> 横屏档位带高度（`宽x高`），**纵溢只在横屏算失败**（`w > h`）：
> 竖屏那套「四家上下堆叠」本来就 ~970px 高，在 860 高的视口里必然要上下滚，那是竖屏的正常交互；
> 横屏的硬要求才是「一屏放得下」。详见「手机横屏」一节。

`check.js` 支持多种写法，随手输都认：

```
123万 456万 789筒 555筒 55条          # 花色写在数字后面
w123 w456 t789 t555 t55              # w万 t筒 s条
一万 二万 三万 ... 东风 红中           # 全中文
东风东风东风 南南南 西西西 北北北 发发   # 字牌也认简写
```

## 界面风格（老吴 2026-10-03「照参考图改界面」）

参考图是别的麻将游戏（3D 透视牌桌 / 深绿台呢 / 底部底分 / 中央大转盘倒计时 / 右上角头像+分数）。
**做了什么、没做什么，先说清楚**：

| 项 | 状态 | 说明 |
|---|---|---|
| 牌面立体厚度 | ✅ 做 | `.tile-face` 用**纯 box-shadow** 加 3px 侧面（分档 3/2/2/1.5px） |
| 绿绒台呢（**真图片**） | ✅ 做 | `body` 底图换成 OpenGameArt 绿垫纹理（CC-BY 4.0），叠顶部受光 + 四角暗角 |
| 中央倒计时转盘 | ✅ 做 | `.center-dial`，**绝对定位**挂在牌河右下角，环形进度 + 大数字 |
| 头像 | ✅ 做 | **本地按名字首字生成**，单机=方位字、网络=真实昵称首字 |
| 累计战绩分 | ✅ 做 | 显示**本场净分**（真实对局成绩） |
| **金币** | ❌ **不做** | 见下方「为什么没有金币」 |
| **真 3D 透视牌桌** | ❌ **不做** | 牌面文字会被拉变形、四方牌无法对齐，得不偿失 |

### 为什么没有金币

引擎里根本没有金币字段（`players` 只有 `seat/name/handCount/melds/discards/opened`），
而且项目红线明确写着**「不做充值 / 金币 / 兑换」（不可撤销）**。
所以既没有真数据、也不该造假 —— 那个位置改显示**真实的累计战绩分**。
参考图那种「底分：300」是它的房间规则，我们这边对应的是真实对局分，不混。

### 3D 桌面排布与尺度（老吴 2026-10-30 十七轮定稿）

所有尺度都由**几何反解**，不写死像素。改这几处之前先读这张表，否则很容易又改回「保守值」。

| 量 | 现行值 | 怎么来的 |
|---|---|---|
| 本家手牌 `MY_HAND_SCALE` | **3.5** | 牌外缘钉在 `EDGE_Z = halfH − 0.020`（压住木框内侧第一行暗带） |
| 对家/上家/下家 `COMMON_HAND_SCALE` | **2.34**（1280×800 实测） | `min(nCapZ, nCapW, ewCap)`，真正瓶颈是 E/W 竖列；1440 宽会略高，窄屏自动降，下限 1.4 |
| E/W 露出率 `EW_EXPOSURE` | **0.76** | E/W 牌沿 z 只有短边 `TILE_W`，叠 24% 肉眼无差；旧版按自然步距求值，等于强制 100% 露出，白扔带宽（1.90 → 2.34） |
| E/W 与本家的缝 `EW_S_GAP` | **0.03** | 列外缘 = `HAND_Z − TILE_H·MY/2 − 0.03`，与本家手牌内缘留 15px |
| 牌河 `RIVER_SCALE` | **1.8**（旧 1.5） | 容量按 `riverColsOf` 反算：S/N 6 列 × 3 行 = 18 张，E/W 3 槽 × 6 段 = 18 张 |
| 牌河横半宽 `RIVER_X_HALF` | **0.265** | 1.8 倍时 0.218 只排得下 5 列，放宽到 0.265 保住 6 列 |
| 座位 x | **E/W 完全对称** = `halfW − cardClear` | 头像卡外缘贴屏（`cardClear ≈ 卡宽 + 4px`）；旧版 W 侧封顶 0.85，是为了给左侧三件套留位 |

**中央罗盘（`#center-indicator` 里的 `.ci-compass`，老吴 2026-10-30 二十一轮）**

- 四字是**固定真实方向**：上北、下南、左西、右东（`net3d-main.js` 的 `CI_COMPASS`，
  下标 = 相对位置 `0下 / 1右 / 2上 / 3左`）。
- 旧版把这四格填成「该位置玩家的风位」（`CI_WINDS[(seat - dealer + 4) % 4]`）：
  庄家坐东 ⇒ 「东」落在下方、「西」落在上方，整盘看起来就是「东、西颠倒」（老吴报的就是这个）。
  方位盘只该表示方向，**不随谁坐哪旋转**；「轮到谁」由箭头 + 该侧高亮表示。
- 想改回「盘上显示四家风位」，得同时解决「我永远在下方 vs 我抽到哪个风位」的矛盾
  （风位是跟着人走的，盘是跟着方向走的），否则必然有一局看着是错的。

**HUD 钉位（DOM 层，`net3d-main.pinFloaters`）**

- 左列三件套：上家卡 → 「不补牌」开关 → 本家卡，竖排夹住开关，全部左缘贴屏（卡片 2~66px）。
- 开关宽度 **60px**（旧 84）：贴边后列左只剩 ~64px，84 会压住手牌列一截。
- 托管条「我要尿尿 / 取消托管」：钉在**下家头像卡正下方 26px**、右缘对齐卡右缘，宽度收成 ≈56px。
  旧版 88px 宽、右缘只到 1274，左边 24px 伸到卡外压住 E 的手牌列。
- ⚠️ 这些样式必须写在**顶层**：写进 `@media (orientation: portrait)` 里桌面横屏不生效（第一版就踩了，量测发现宽度仍是 88）。

**坑：昵称首字被削。** 卡片里的名字是 `text-align:center` + `overflow:hidden` + `ellipsis`，
文字比盒子宽时两侧一起溢出、**左边被裁掉**（显示成「n3_hd9…」，开头的 m 少一半）。
必须 `text-align:left`，超宽才只在右侧打省略号。

**左上角癞子徽标（`#wild-badge`，DOM 覆盖层）**

- 内容只有两件：**牌面图 + 一个黄底深绿的「赖」字**（老吴 2026-10-30 十八轮：不要文字）。
  牌名不进视觉，退化到 `title` / `aria-label`（`癞子 八筒`），悬停与读屏仍可读。
- **顺序与等高（老吴 2026-10-30 二十轮）**：「赖字显示在牌面的**左侧**，汉字和牌面**大小齐高**」。
  DOM 改为 `<b>赖</b><img>`；字块高度直接取 CSS 变量 `--wild-tile-h`（和牌面同一个变量），
  所以两者**永远等高**，以后单独调牌面不会再一高一矮。
- 字号是**反推**的，不是拍脑袋：实测 PingFang SC 800 的「赖」墨迹高 = **0.941em**
  （`canvas.measureText` 的 `actualBoundingBoxAscent + Descent`，不是想当然的 0.88），
  要让墨迹正好等于牌面 52px ⇒ `52 / 0.941 ≈ 55px`（58px 会高出 2.6px、字顶到黄块边沿）。
  行框 55px 比块高 52px 多 3px，flex 居中后上下各留 1.5px，`overflow:visible` 不裁字。
- 尺寸：牌面 **52px**、赖块 **65×52**（`padding 0 5px`，块高 = 牌面高）、方胶囊 `border-radius: 12px`，
  整枚 **≈124×62**（旧版「癞子 三条」≈135×41）。两处细节是踩出来的：
  ① 源图自带白面与立体边，再垫 `background:#f6f0dd` 会多一层直角白框 → 必须 `transparent`；
  ② `border-radius:999px` 全圆会让方角牌图的四角顶出弧线 → 用方胶囊。
- N（对家）卡的避让**不写死宽度**：`render3d` 每帧读 `offsetWidth` 算 `badgeRight`
  （`12 + 徽标宽 + 6`）。改徽标尺寸只需改 CSS，卡片会自己让开。
- ⚠️ `tools/verify-net3d-play.mjs` 断言 `text === '赖'` 且 `title` 含「癞子」——
  想再加字就会被显式判红，别绕过。

**桌上不再摆骰子与癞子指示牌（老吴 2026-10-30 二十轮：「牌河中不要显示骰子和赖子了」）**

### 三条硬约束（改这块界面时务必先读）

1. **一律只改颜色 / 阴影 / 纹理，绝不动盒模型与布局。**
   「页面高度恒定」是硬红线（见上一节），任何 `padding` / `border` / `height` 的改动都可能顶高整桌。
2. **头像 ≤ 21px**（= `.dir-badge` 的直径）。上/下两家在 grid 的 `auto` 行，
   头像一旦更大，座位行就变高 → `#table` 变高 → 整页抖动。`viewport-check` 会显式断言这一条。
3. **转盘用绝对定位**（`.center` 加 `position:relative` 作定位上下文），

### ⚠️ 换背景时踩到的既有 CSS bug（已修）

改背景时实测发现 `getComputedStyle(body).backgroundImage` 只有 1 层、`background-size: auto` ——
**上一版的菱形暗纹 + 受光渐变从来没生效过**，页面一直是纯色。根因：
`html, body { background: var(--felt) }` 这条 **`background` 简写**排在 `body{background-image:…}` **之后**，
简写会把 `background-image` 一起重置成 `none`。现已把 `html` / `body` 拆开、各管各的层。
**教训：背景一律用 `background-color` + `background-image` 分开写，别用 `background` 简写。**

### 座位与方位（老吴 2026-09-30 改版）

开局先**摸风定座**，再开打：

| 环节 | 规则 |
|---|---|
| 摸风 | 四家各抽一张（**牌面互不相同**，避免"两张一样的牌怎么比"的死结）。**牌最大者坐东并做庄**，其余按大小依次南 / 西 / 北 |
| 比牌 | **数字牌 > 字牌**（"风牌比数字都小"）；数字牌按**点数**比，9 最大，同点按 万 < 筒 < 条；字牌按 **东 > 南 > 西 > 北 > 中 > 发 > 白** |
| 屏幕排布 | **你永远在下方**；出牌逆时针 → 下家在右、对家在上、上家在左。座位上的**方位徽章（东南西北）随摸风结果旋转** |
| 庄家 | 恒等于东家（`seatToDir[dealer] === '东'`，有测试守着） |

> 方位是**座位的属性**（摸风定），屏幕位置是**你的视角**（固定）。两者正交，所以"上家"可能在左，
> 也可能带"东"或"南"的徽章。顶栏有一行速查：`你=西 · 下家=北 · 对家=东 · 上家=南`。

不用摸风时（`createLocalGame({ drawWind: false })`）退化成「随机庄家 → 庄家坐东，其余依次南/西/北」。

#### 手机竖屏 → 自动横屏（老吴 2026-10-09）

需求原文：「**我需要当用手机打开时，根据屏幕大小，自动横屏展示，并且页面大小固定不动**」。
方案经老吴拍板：**CSS 旋转 90°**（不用 `screen.orientation.lock()`—— iOS Safari 不支持，
且要全屏 + 用户手势 = 每次进游戏都多点一下，桌面浏览器也不该被锁）+ **仅手机竖屏生效**。

```css
@media (orientation: portrait) and (pointer: coarse) {
  html, body { overflow: hidden; overscroll-behavior: none; }
  body {
    position: fixed; inset: 0;
    width: 100vh;/* 屏高 = 旋转后的逻辑宽度 */
    height: 100vw;   /* 屏宽 = 旋转后的逻辑高度 */
    transform: rotate(90deg);
    transform-origin: center center;
  }
  #app { height: 100%; max-width: 100%; overflow: hidden; }
  .topbar h1 { display: none; }
  body { touch-action: manipulation; }
  .flash  { left: 50%; top: 8px; bottom: auto; }   /* 旋转后 bottom 会弹到侧边 */
}
```

| 设计点 | 为什么 |
|---|---|
| **核心换算**：旋转后「逻辑高度」= 竖屏时的**视口宽度**（390/414/360…） | 所以上面三档横屏断点用 `@media` **逗号并列**加 `(orientation:portrait) and (pointer:coarse) and (max-width:Npx)`，N 与原 `max-height:N` **一一对应**，规则体只写一遍，不存在两份样式漂移 |
| 必须挂 `pointer: coarse` | 否则「桌面浏览器开窄窗口」（500×900）也会被转 90°，桌面用户直接懵 |
| `transform` 而非改 `height`/`width` | transform 是**绘制层**变换，不参与布局计算 ⇒ 不破坏「高度固定」红线，也不触发重排 |
| `overflow:hidden` + `overscroll-behavior:none` | 一旦能滚，旋转中心就会漂，整页歪掉 |
| safe-area 让给左右 | 横过来之后刘海/圆角跑到左右两侧去了（`env()` 不支持时回退 0，安全） |
| `.flash` 从 `bottom` 改 `top` | 它是 `left:50% + translateX(-50%)` 居中，旋转后 `bottom` 变成「离左边 18px」，提示会弹在侧边 |

实测（无头 Chrome + CDP，6 档）：`393×852` / `375×667` / `360×780` / `430×932` 四档手机竖屏
**全部正确转成横屏**（body 逻辑宽高交换、视觉框正好铺满视口、横屏档命中、大标题隐藏）；
桌面窄窗口（500×900，`pointer:coarse=false`）与真横屏（852×393）**正确不转**。

> 🔴 **2026-10-24 修「3D 网络版没按合适分辨率展示」**：`net3d.css` 的 `#play { height:100dvh }`
> 在旋转后的 body 里取的是**物理屏高**（844），而 transform 元素是 fixed 后代的包含块，
> 旋转后的逻辑高度应是**屏宽**（390）⇒ 画布纵向溢出大半。修法：竖屏档内改 `#play { height:100% }`
> （= 旋转后 body 的高度），且必须写在 `#play` 基础规则**之后**（同特异性，后写赢）。
> 验收：无头 Chrome 以 390×844 + `pointer:coarse` 仿真，`DOMMatrixReadOnly` 判旋转 +
> `#play.offsetHeight === 390`（量布局尺寸用 offsetHeight，老规矩）。

> 🔴 **量旋转后的尺寸必须用对 API**（这一条让我绕了很大一圈）：
> `getComputedStyle().transform` 对 `rotate(90deg)` 返回 **`matrix(0,1,-1,0,0,0)`**，
> **字符串里没有 "90"** —— 用 `includes('90')` 判定会得到「全都没转」的假警报。
> 正确写法：`new DOMMatrixReadOnly(cs.transform)` 看 `m11≈0 && m12===1`。
> 同理，旋转后 `getBoundingClientRect()` 返回**视觉包围盒**（852 宽 × 25 高的 topbar 转 90°
> ⇒ 包围盒 25×852，报 height=848）⇒ **量布局尺寸要用 `offsetWidth/offsetHeight`**。

#### `viewport-check` 的横溢判据：`hOver` 而不是 `overflow`（2026-10-09 修的真实盲区）

`#app` 是 `overflow-y: auto`，按 CSS 规范 `overflow-x: visible` 会被**降级成 `auto`**
⇒ 内容横向出界时被 `#app` 自己吃掉，`documentElement.scrollWidth` **压根不涨（`overflow = 0`）**，
但元素右边界确实超出了视口。所以判据取两路最大值，9 处失败判定 + 「取最难一局」的挑选全部改用它：

```
hOver = max(documentElement.scrollWidth - vw,最出界元素的 right - vw)
```

**豁免规则** `inScrollableX(el)`：祖先链上有 `overflow-x: auto/scroll` **且 `scrollWidth > clientWidth`（真能滚）**
⇒ 子元素超出**不算 bug**。`#me-hand { overflow-x: auto }` 是有意设计（响应期我手牌 14 张、容器 324px 装不下，
本来就该横滑），不加这条豁免会误报 `hOver = 28`。
⚠️ 只是 `overflow-x: hidden`（内容被吞掉、用户看不到）**不算**豁免 —— 那仍是 bug。

#### 牌桌不再拉伸填屏 + 操作区搬进「我的座位」（老吴 2026-10-01）

老吴原话：**「本人的牌局要往上挪，都放到桌子上，牌河不需要空那么多空间，吃、碰、杠、胡等按钮在具备条件时显示在牌的上方」**。

- 打不出去的牌（例如无癞子的普通牌撞上杠）会在底部闪一句一次性提示（1.6 秒自动消失）。

### 入会申请（老吴 2026-10-30：进俱乐部要创建人同意）

原来 `POST /clubs/:id/join` 是**自助入会**：谁点谁进，主席连有人进来都不知道。现在是申请制：

| 环节 | 接口 | 行为 |
|---|---|---|
| 提交申请 | `POST /api/clubs/:id/apply`（`/join` 为别名） | 只写 `club_applications` 一行 `pending`；已是成员回 `member:true`，已排队回 `already:true` |
| 看谁在排队 | `GET /api/clubs/:id/applications` | **仅 owner/admin**，普通成员 403；俱乐部详情里也只对管理者下发 `applications` |
| 同意 | `POST /api/clubs/:id/applications/:uid/approve` | 写成员行 + 申请置 `approved`；审批限速 30 次/分/IP |
| 拒绝 | `POST /api/clubs/:id/applications/:uid/reject` | 只改状态，允许对方之后再申请（会重新置回 pending） |
| 撤回 | `DELETE /api/clubs/:id/applications/:uid` | **只能撤自己**的（uid 不等于自己 → 403） |

数据落在新表 `club_applications(club_id, user_id, status, note, created_at, decided_at, decided_by)`，
主键 `(club_id,user_id)` —— 一个人对一个俱乐部只有一行，重复申请就是改这行，不会把待审列表刷爆。

界面：大厅「可加入的俱乐部」按钮在 **申请加入 ⇄ 撤回申请** 之间切换，行内提示「申请已提交，等待主席同意」；
主席进俱乐部后「入会申请 N 条待审」区每条都有「同意 / 拒绝」，审批后成员表与成员数当场刷新。
「我的俱乐部」列表上也会标 `· N 条入会申请`（只有管理者拿得到这个数）。

> 两个 UI 细节是截图量测才发现的，别再踩：①三个子元素直接塞进 `.lb-item`（`justify-content: space-between`）
> 会把「同意」摊到行中间，两个按钮必须包进 `.lb-item-actions`；②`h2` 里若把标题文字和 `lb-count` 当两个独立
> 子元素，计数会被推到中间，要用一层 `<span>` 包成一组。

### 一个渲染层，两个驱动

`frontend/render.js` 只管「拿到一份 view 就画出来」，**一行对局推进逻辑都没有**；
谁提供 view、点了按钮之后怎么走，由注入的 driver 决定：

| | 单机版 `frontend/main.js` | 网络版 `frontend/net-main.js` |
|---|---|---|
| driver | `createLocalGame()`（本地引擎 + 3 机器人） | `createNetDriver()`（socket.io，服务端权威） |
| 出招 | `humanAct()` → `botStep()` → 同步拿到新 view | `emit('action')` → 等 `table:state` 回来才有新 view |
| 超时自动过 | 前端自己倒计时并代发 `pass` | **`autoPassLocally = false`**，交给服务端兜底（`armClaimTimer`），前端只显示倒计时，避免两边各发一次 |
| 摸风面板 | 本地摸风定座 → 弹面板 | `winds.entries = null` → 不弹（定座由服务端决定） |
| 听牌分析 | 本地算（`analyzeTenpai`） | **服务端下发**（客户端拿不到 `claims`，也算不了） |

driver 契约（两者必须完全一致，`net-driver.js` 头部有完整注释）：
`seatToDir` / `winds` / `actingSeat()` / `isMyTurn()` / `getView()` / `getTenpai()` / `ruleset` / `autoPassLocally`。

### 服务端每帧多发三样东西（`server/ws/room.js` `statePayload()`）

| 字段 | 为什么 |
|---|---|
| `actingSeat` | 响应阶段到底轮到谁，客户端看不到 `claims`，判断不了 |
| `dealer` | 前端据此推「座位 → 方位」（庄家坐东，依次南 / 西 / 北） |
| `tenpai` | 听牌分析必须有完整引擎状态；实测 **0.91ms/次（p90 2.74ms）**，四座位一帧约 3.6ms，放进广播比让客户端再往返一次划算 |

> ⚠️ `table:state` 的 `view` 对局中**永不含别家手牌**（沿用 `viewFor` 的硬约定），
> 只有 `phase === 'settled'` 那一帧才带摊牌手牌。

### 长断线：托管（老吴 2026-10-02；「判离席作废」已取消；2026-10-02 后续「自动托管」也已取消）

`claimTimeoutMs` 只兜得住**响应阶段**：他人打牌后 N 毫秒没人响应就代其「过」（`armClaimTimer`）。
它兜不住另一件更常见的事 —— **轮到某人出牌时他掉线了**。此时 `armClaimTimer` 因为
`phase !== 'claim'` 直接返回，整桌就永远卡在那里看牌背；「等待下一把」期间有人不点「准备」
同样卡死。于是需要「托管代打」来兜底。

**两个核心结论（老吴 2026-10-02 拍板 + 后续需求）：**
1. 客户端断开再久，牌局也不结束；玩家重连即回到原牌局继续 → **自动判离席（长断线作废整场）已移除**。
2. **断线不再自动托管**：必须由某位在线玩家**主动点「托管」按钮**才托管。取代原先「断线 24s 自动
   转托管」的做法，避免在无人确认的情况下把断线者的牌局交给机器人。

**断线后重新进入：直奔牌桌（老吴 2026-10-30）：**
- 前端把「当前牌桌」记进 `localStorage['mahjon:net:lastTable']` = `{tableId, clubId, at}`，
  在桌期间 `table:players` 每来一帧就刷新 `at`（长局不因 TTL 过期被丢）；**TTL 12 小时**。
- `boot()` 登录成功后有记录就走 `resumeLastTable()`：先用 `clubId` 把 `S.club` 复原（牌桌页的
  「返回俱乐部 / 离桌」不用再查一遍），再 `enterTable(tableId)` 拿回座位。
- ⚠️ **有记录时先不展开俱乐部页**。旧写法是「先 `showLobby('clubs')` → `loadClubs()` → 再回桌」，
  会先闪一帧俱乐部列表再跳进牌桌，体感仍然是「进来停在俱乐部」。现在只挂 `#waiting`
  （「正在回到上一张牌桌…」），拿到结果再决定给牌桌还是给列表。
  `tools/verify-reconnect.mjs` 用逐帧采样断言这件事（`__sawClubsBeforePlay === false`），已有反证。
- 回不去就安静落回俱乐部列表并提示原因：牌桌不存在 / 已被移出俱乐部 / 记录超过 TTL / 记录损坏。
  失败一律 `clearLastTable()`，不会反复重试。
- **主动离桌**（`leaveTable`）与**投票结束整场**（`table:exited`）都会清掉记录 ——
  否则下次开页面又把人拽回一张空桌。

**掉线玩家的头像置灰（老吴 2026-10-30）：**
- 数据源是 `table:players` 的 `connected`，服务端在断线 / 重连时都会广播这一帧，
  所以**不依赖下一帧 `state`**，掉线那一刻立刻变灰、重连那一刻立刻复原。
- `render3d.setOnline(seat→bool)` 只切一个 `.offline` 类；CSS 对 `.avatar` 施加
  `filter: grayscale(1) brightness(0.72) contrast(0.9)`。庄 / 番角标与得分不动 —— 信息还能用，
  但一眼看出「这家现在不在」。
- 回放没有 socket，`onlineMap` 恒为 `null` ⇒ 全部按在线处理（避免回放里一片灰度）。

**托管按钮在哪 / 谁能点：**
- 大厅座位卡（未开局）与牌桌顶栏 `#host-controls`（开局后常驻）都会给「断线座位」显示「托管」按钮
  —— 任何在线玩家都能点，把该断线座位交给服务器代打。
- 自己的座位在在线状态会显示「我要尿尿」—— 你要走开前自托管，回来重连即撤销。
- 已托管的座位显示「取消托管」。
- 网络层权限（`table:setAbsent`）只放行「本人」或「已断线的座位」，在线的其他玩家**不能**被托管。

| 开关 | 默认 | 含义 |
|---|---|---|
| `offlineAutoPlay` | `true` | ⚠️ 已废弃：托管完全由按钮（`table:setAbsent`）驱动，不再自动触发，字段保留仅为兼容 |
| `offlineAbsentMul` | `3` | ⚠️ 已废弃：旧的「断线 24s 自动托管」阈值，现由手动按钮取代 |
| `offlineDissolveMul` | `15` | ⚠️ 已废弃：旧的「断线 120s 判离席」阈值，2026-10-02 已取消自动判离席 |

四个设计要点：

1. **`Room.sweepOffline(now)` 仍是纯决策、不含定时器**，但**只驱动「已托管」座位的代打 / 自动 ready**：
   定时器在 `server/ws/index.js` 的 `armSweep()` 里，只挂「已托管」座位（手动按钮触发）。
   `Room.setAbsent(uid, on)` 负责人工切换 `absent` 标记。
2. **判定顺序**：先由按钮把座位置 `absent`（及其权限校验）→ 再由 `sweepOffline` 代打。托管成立后就由
   服务器继续推进，牌局不会再卡死。
3. **托管 ≠ 响应超时**。超时是**保守**代打（只「过」，不进攻）；托管是玩家已明确不在，于是**正常代打**
   （能胡就胡、能碰就碰）—— 两者用同一套纯函数引擎，只是策略不同。
4. **无人观战时整桌「挂起」**：若所有座位都离线，巡检与代打都暂停（不空转、不替所有人自走），
   任一人重连即唤醒并续局。

托管期间牌局持续推进；**玩家重连 → 撤销托管、拿回原位、从当前状态继续**，不会再出现「四个人卡死等一个」。

前端事件（`table:dissolved` 已不再自动发出，仅保留为将来手动解散预留）：

| 事件 | 触发 | 前端 |
|---|---|---|
| `table:setAbsent` | 在线玩家点「我要尿尿 / 取消托管」 | 服务端做权限校验后切换该座位 `absent` 并广播 |
| `table:absent` | 某座位被托管 / 取消托管（手动，带 `manual/on` 标记） | 状态条提示「X 已被托管，由服务器代打」或「已取消托管」 |
| `table:resumed` | 本人重连、托管撤销 | 提示「回到座位，托管结束」并补拉一帧最新视图 |

座位格三态**互斥**：`托管中`（琥珀色）> `断线`（红色）> 正常。`table:players` 里每个座位
多了 `absent` / `botSteps` 两个字段，房间状态条上托管座位记 `🤖`。

> `verify-net-e2e.mjs` 的 ⑤ 段真跑一遍：断开 0 号 → 由 1 号发 `table:setAbsent {seat:0,on:true}` 主动托管
> → 收到 `table:absent`（带 `manual` 标记）→ 从 1 号视角观测 0 号牌河变长（**证明服务器真的在替它打牌**）
> → 超过原判离席阈值后断言**无 `table:dissolved`、座位仍保留** → 0 号重连拿回原座位，牌局续上。

### 打满设定局数后的本场总成绩

打满「圈数 × 4」把后，服务端先结算最后一把，再发 `table:finished`，前端弹出总成绩弹窗。

> **顺序：先本局、后本场（老吴 2026-10-30）**「本场次游戏结束时，先弹出本局的结算，确认后再弹出本场次的结算信息」。
> `table:finished` 到达时 `#settle`（本局结算）正开着 —— 旧版直接把本场窗叠上去，本局等于没看。
> 现在 `exit-game.js` 把它**暂存**在 `pendingFinal`：只有 `reason === 'finished'` 才排队，
> 玩家点结算窗的「结束」＝确认本局 → `onNewGame` 走 `showPendingSummary()` 弹本场。
> - 排队期间**不**把 `#settle` 设 hidden：后面任何 `renderAll` 都会按「phase 仍 settled」把它重新打开，
>   两张窗又叠一起。本场窗在 DOM 里排在 `#settle` 之后、同为 `z-index:800`，天然在上层；
>   关掉它时走 `onDone` 离桌，由 `leaveTable()` 统一收掉 `#settle`。
> - **投票退出不走排队**：那是中途散场（当前这把不计），`#settle` 可能再也不会被关（view 已置空），
>   排队等于永远不弹 ⇒ 该路径直接收掉本局窗、立刻弹「本场结束」。
> - 本场窗的按钮据此改成**「返回俱乐部」**（牌桌已经结束，旧文案「返回牌桌」是假的），点掉即离桌。
>
> **本场窗横屏化（同轮）**：「本场次的结算信息页面是竖屏页面，未调整成横屏页面」——
> 它此前没有任何专属样式，只吃 `style.css` 的 `.modal-card` 默认值（460px 宽 + `88vh` 限高）：
> ① 7 列表格被挤到换行，② `88vh` 按**物理**竖屏高算（旋转后可视高只有屏宽），卡比可视区还高。
> `net3d.css` 现在按 `#settle` 的同一套口径给它补了规则：宽度 `min(98%, 780px)`（旋转态禁用 vw 钳制）、
> 限高 `92%`（按包含块算）、表格外面单独包一层 `.exit-table-wrap` 内部滚动
> （给 `<table>` 自己加 `overflow` 会把表格变成块、列宽全错），单元格 `nowrap`；
> 1280×800 实测 780×320、7 列一行放完、无内滚；844×390 实测 138px 表格区仍无溢出。

### 退出游戏投票（老吴 2026-10-21）

牌局进行中（含「等下一把」）顶栏有「退出」按钮。点击后向另外三家发起投票：

- **三家全部同意** → 整场立即结束，`finished=true`、牌桌回 `idle`，弹出最终积分。
- **任意一家不同意** → 请求作废，牌局继续；可以重新发起。
- 最终积分由服务端按 `Room.completedResults` 累计，**只算已经完成/已结算的牌局**；
  当前没打完的这把不计入。若本把已结算但还在摊牌确认，则它算已完成。
- 退出时当前这把不写回放，也不补记本把战绩；之前已完成牌局的回放与战绩保留。
- 机器人座位不是真人，发起时自动视为同意；真人座位必须各自投票。
- 参与投票的座位**断线或主动离开** → 申请自动作废，避免其他三家被弹窗永久挡住。
- 投票状态写进 `table:players.exitVote`，断线重连后仍能恢复投票界面。

| 事件 | 方向 | 含义 |
|---|---|---|
| `table:exitRequest` | C→S | 发起退出申请；已有申请时只有发起人幂等成功 |
| `table:exitVote` | C→S | 另外三家投票 `{agree:false}` 立即作废，`{agree:true}` 累计 |
| `table:exitRequested` | S→C | 新申请（含 `fromSeat/fromName/approvals/needed/completedHands`） |
| `table:exitUpdated` | S→C | 同意进度更新 |
| `table:exitRejected` | S→C | 某家拒绝，牌局继续 |
| `table:exitCancelled` | S→C | 断线 / 离开 / 本场自然结束导致申请作废 |
| `table:exited` | S→C | 三家全同意，下发 `completedHands` 与四家 `standings` |
| `table:finished` | S→C | 打满设定局数，下发 `completedHands` 与四家 `standings`（含总得分/胡牌/点炮/金顶/连庄） |

### ⑤ 个人总成绩：**跨俱乐部**，不分俱乐部

老吴 2026-10-03 定的口径：**一个人在所有俱乐部打的牌，全部计入同一份个人总成绩**。
所以从任何一个俱乐部页点「我的战绩」，看到的数字都一样 —— `clubId` 只用来做
「俱乐部存在 + 我是成员」校验，**不参与统计**（响应里 `scope: 'all-clubs'` 明示这一点）。

五个指标（对应老吴点名的「胜率、大胡率、金顶率、总成绩、总平均分」）：

| 指标 | 算法 |
|---|---|
| **总成绩** | 累计净分（收 − 付），就是界面上的头号大数字 |
| **胜率** | 胡牌局数 ÷ 总局数 |
| **大胡率** | 大胡局数 ÷ 总局数 |
| **金顶率** | 金顶局数 ÷ 总局数 |
| **总平均分** | 总成绩 ÷ 总局数（每局平均净分，正就是赢、负就是输） |

> **三个率的分母统一是「总局数」**，荒庄照样计入 —— 荒庄也是一手牌，把它藏起来会让胜率虚高。
> （平均番是例外：分母只取 `fan > 0` 的局，0 番局拉低均值没有信息量。）

### 数据从哪来：一个 `result.perSeat`

引擎在**每把结算**（胡牌 `settleWin` / 荒庄 `settleDraw`）都往 `state.result.perSeat` 塞一个结构化数组：

```js
[{ seat, name, isWinner, delta, fan, gangs, huType }, ...]   // 四家各一行
```

四个维度 + 后端落库**全部复用它**，所以不存在「界面一套算法、落库另一套算法」的漂移。
`huType` 只有 `small` / `big` / `gold` 三种，荒庄时四家 `delta = 0`。

### 三张表的分工

| 表 | 维度 | 用途 |
|---|---|---|
| `user_career_stats` | **只按 user_id** | ⑤ 的 `period=all`；**含个人统计上线前的历史**（启动时一次性回填） |
| `hand_records` | user_id（**不带 club_id**） | ⑤ 的日 / 月 / 年时段口径；索引 `idx_hand_records_user_ts(user_id, ts)` |
| `player_stats` | club_id × user_id | ④「跨场战绩榜」专用，**不参与个人统计**（否则就不是「总成绩」了） |

每次结算在 `server/ws/index.js` 的 `recordStats(room)` 里**并列**写三张表。

> **回填只做一次**：`app_meta.career_backfill_v1` 打标记。回填时 `hands/wins/net/gold_tops/gangs/max_fan`
> 从 `player_stats` 的 SUM 取（那是权威累计值），而 `small_hus/big_hus` 只能从 `hand_records` 的
> `hu_type` 统计 —— 这是**纯计数**、与前者不重叠，混起来不会重复计数。

> ⚠️ 写流水必须用事务。`node:sqlite` 的 `DatabaseSync` **没有** `.transaction()`（那是 better-sqlite3 的 API），
> 所以 `server/db.js` 自己实现了 `inTransaction(fn)` 手写 `BEGIN / COMMIT / ROLLBACK`，
> 三个 `record*` 函数统一走它 —— fn 抛错必须回滚，否则事务一直挂着、后续写入全失败。
> （早前 `recordHandStats` 误用了 `db.transaction()`，是一个真实 bug，已修。）

### 时段口径

`periodRange(period, nowSec)` 用**服务器本地时区**切日/月/年，返回半开区间 `[from, to)`。
不用 SQLite 的 `strftime(..., 'localtime')` —— 那在部分构建上不可靠；NAS 上本地时区与 `date` 一致。

白名单只有 `day | month | year | all`，非法值（如 `?period=xxx`）**回落 `all`**，防注入。

### API

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/clubs/:id/my-stats` | **⑤** 本人四口径一次返回 `{me:{scope,day,month,year,all}}`，跨俱乐部；仅成员可见（非成员 403、未登录 401） |
| `GET` | `/api/clubs/:id/stats?period=day\|month\|year\|all` | **④** 俱乐部榜（**按俱乐部隔离**）。`all` 走 `player_stats`（返回 `total_score`），其余走 `hand_records`（返回 `net`） |


### 前端

`frontend/stats.js` 是**驱动无关的纯函数模块**（零 DOM）：`createMatchStats()` 工厂，
方法 `reset() / addHand(perSeat, handNo, type) / getMatchStats() / getDetailRows() / hasData()`。
两个 driver 各建一个实例（网络版在 `table:started` 且 `handNo === 1` 时 `reset()`），
通过 `render.js` 的 `setMatchStats(ms)` 注入 —— 渲染层依旧**不含任何推进逻辑**。

顶栏「战绩」按钮**始终占位**，只在无数据时 `disabled` 置灰（与「新局」「听牌提示」同一约定），
不能 `display:none` —— 否则结算后按钮出现会把顶栏挤宽 → 座位行文案换行 → 顶栏变高 → 牌桌被偷走十几像素。

### 癞子 / 皮子 / 红中 —— 三张牌三套逻辑（最容易搞混的地方）

| 牌 | 角色 | 关键约束 |
|---|---|---|
| **癞子** | 万能牌，可替代任意牌 | 打死不打；杠掉它很亏（`gangFan.wild = 2`） |
| **皮子** | = **癞子往回数 2 张 + 红中**（共 3 种 **11 张**） | **留手不能胡**；不吃不碰；可以单独拿出来杠（皮子杠） |
| **红中** | **不是万能牌**，是固定杠牌（同时算一种皮） | 留手不能胡；可以随时杠（红中杠） |

**皮子怎么数出来的（老吴 2026-09-30 口径）**：以**癞子**为基准往回数——

```
翻出五万 → 六万是癞子 → 皮子 = 五万（癞子减一）＋ 四万（癞子减二）＋ 红中
                                        ↑ 五万那张已被翻出、不再可用，剩 3 张
                        合计 = 3 + 4 + 4 = 11 张  ✓
```

任何一张翻牌都是 **11 张**：翻一万 → {一万(3), 九万(4), 红中(4)}；翻北风 → {北风(3), 西风(4), 红中(4)}。
回推方向与癞子同规则：**数牌同花色内循环**（一万 → 九万）；**字牌跳过红中**（癞子发财 → 减一北风、减二西风）。
`skinPrevCount` 控制回推张数：`2` = 十一皮（默认）；`3` = 十五皮；配 `skinIncludesRedDragon:false` = 七皮。

三者都不算「开口」，也都不折算面子（见下方「面子折算」）。

### 杠后不摸牌（老吴 2026-10-21 提出，2026-10-24 定稿口径）

「杠后不摸牌（仅加番）」开关**只对红中杠 / 皮子杠 / 癞子杠生效**：勾选后点这三类杠
（或双击红中/皮子/癞子）带 `noDraw:true`。

- **为什么只有特殊杠可以不摸牌**：红中/皮子/癞子杠只走 **1 张牌**，等价于**打出了一张牌**
  —— 所以不补摸、杠完照常**换手到下家**；自己手牌比应有张数少 1，
  下次轮到摸 1 张即对齐，与「打过一张牌」的正常节奏完全一致，**不存在欠张**。
- **暗杠 / 蓄杠 / 明杠（zhi）占面子，必须补摸**：即使客户端带了 `noDraw`，
  引擎在 `act()` 里一律剥掉（2026-10-24，防旧客户端误带）；补摸后仍是自己的出牌回合。
- 特殊杠的 noDraw **不会算杠上开花**（`gangFlag` 被清空）；占面子的杠照常补摸、照常可杠上开花。
- 杠的番照常加；开关是**一次性的**：执行任何动作后自动复位，不跨回合保留；默认不勾选。
- 界面：开关只在**有红中/皮子/癞子杠可选**时出现，文案「杠不摸牌（红中/皮/赖）」；
  点击特殊牌直接执行（双击红中/皮子/癞子 = 对应杠），按是否勾选决定带不带 `noDraw`。
- 回归：`test/game.test.js`「红中杠 / 皮子杠 / 癞子杠 = 等同打出一张，不摸牌直接过手」
  「暗杠必须补摸（noDraw 被剥离）」「蓄杠 noDraw 被剥离」「明杠 noDraw 被剥离」。

### N 番起胡的门槛怎么算（老吴 2026-09-30 明确）

门槛衡量的**不是赢家自己一个人的番数**，而是 **赢家番 ＋ 每一个输家的番数**：

```
effFan(某输家) = 赢家总番 + 该输家自家番
只有当【每一个输家】的 effFan 都 ≥ 门槛（小胡 6 / 大胡 3）时，才允许胡牌
```

- 实现：`enforceMinFan`（总开关）+ `minFanCountLosers`（默认 `true` = 逐家判；设 `false` 退回旧口径「只看赢家自己」）
- 引擎入口：`canWinWith()` → `worstEffFanForWin(state, seat, winnerFan, context)` 取**最差那一家**兜底
- 门槛恰等于分段计分表的**最低档** → 能胡即保证三家都至少得 1 分，**杜绝 0 分结算**
- 副作用（600 局实测）：**20.0% 的胡牌局**是「赢家自身番不够门槛、靠输家番凑够」才放行的，**全部是小胡**；赢家最低番可低至 **2 番**
- 反向拒绝示例：赢家 4 番 + 三家 2/2/1 番 → 有一家只到 5 番 → 拦下，提示
  `番数不够（赢家 4 番 ＋ 玩家4 1 番 = 5 番，小胡需每家都 ≥ 6 番起胡）`

### 下雨 / 陪包（老吴 2026-10-25 定稿口径）

> 「下雨是指：当某个玩家 A 已经有**两个同一门花色的明牌副露**（暗杠不影响），有其他玩家 B
> 继续打出该花色，被玩家 A 吃或碰或杠了，则玩家 B **包胡**。其他玩家必须打出清一色的那一门
> 花色，这个动作称为**下雨**。不下雨则**陪包**——和包胡者输一样的分数，最多三家（陪）包，
> 极端情况下该局胜者的得分相当于普通局的得分乘以 9。风一色是特殊的清一色，打出第三句的玩家
> 不用包胡。将一色也算清一色，如果有人包胡，也需要下雨。」
>
> ⚠️ 这套「**明牌计数、暗杠不影响**」的口径，2026-10-29 起**同样用于一色包的「第三句」判定**
> （`thirdColorMeldProvider`）：吃/碰/明杠/蓄杠都占位，暗杠与三种特殊杠不占位。
> 例：`碰 → 碰 → 暗杠 → 碰`，第 4 个碰才是第 3 个明牌副露 → 它的供牌者包胡。

| 项 | 口径 | 实现 |
|---|---|---|
| **包胡触发（实时宣告）** | A 的某花色**明牌副露**（吃/碰/明杠/蓄杠；**暗杠不计**）被喂到**第 3 句** → 供牌者包胡。**第 4 个明牌不包**，除非前三句里有暗杠（暗杠计数位移，第 4 句实际是第 3 个明牌 → 照包）——老吴 10-25 修订② | `checkRainDeclare`：只在该花色明牌副露**恰为 3** 时宣告；`state.rains[]` 按宣告先后排序 |
| **下雨义务** | 宣告后，除雨主与包胡者外的玩家出牌时必须打该花色；**第一种花色下完才轮到第二种**（多场雨按宣告顺序） | 前端：义务人出牌提示 + 手牌雨花色牌蓝描边（`.rain-tile`，纯 outline 零布局） |
| **陪包判定（修订③）** | **逐轮出牌**判：出牌时**手中有该花色却未出** → 当场记陪包（不看结算手牌） | `doDiscard → checkRainPenalty`，记入该雨的 `penalties[]`，日志当场宣告 |
| **结算条件（修订①）** | **雨主自己胡牌**才结算该雨的包/陪；A 没胡 → 谁胡按谁的牌面正常算分，包胡下雨全不计算 | `finishWin`：`myRain = rains.find(owner === winnerSeat)` |
| **金额（修订④确认）** | 包胡者、陪包者**各付该局总分**（不均摊）；其余免付。三家全掏 = 总分 ×3 ≈ 普通单家的 9 倍（对称局，即「乘以9」） | payments 重写 + `result.rainPayers = [{seat, kind:'bao'\|'pei', amount}]` |
| **惩罚范围（修订⑤）** | 惩罚只挂**第一场**被包的花色；第二场被包的花色**不算下雨惩罚**（只约束出牌顺序） | `peiSeats` 仅取 `rains[0].penalties` 且雨主胡牌 |
| **风一色** | 不包不下（直接金顶，既有口径）；字牌副露本身不会触发下雨 | 雨花色只可能是万/筒/条 |
| **与「第三句包」的关系** | 既有「清/将一色第三句包」（要求赢家做成清/将一色）**保留**，与雨包取**并集**（跨花色将一色只有旧口径能覆盖）。⚠️ 2026-10-29 起**一色包整体优先于全求人包**：只有 `colorBao` 为空（非一色，或明副露不足 3 口）才回落到「放炮者包」 | `resolveThirdMeldBaoSeats ∪ myRain.baos` → 非空即用；为空再走 `resolveQuanQiuRenBaoSeat` |
| **全求人将牌豁免** | 下雨义务人手里**最后仅剩该花色的将牌**时打出该将、点炮给全求人 → **不包全求人**（被规则逼着打的） | `isRainJiangExempt`（只看第一场雨）：winTile 是雨花色 2/5/8 且放炮者手牌（打出后）全是该花色将牌或癞子/皮子 |
| **建桌开关** | `rainEnabled`（默认开） | 规则面板「番/封顶/特殊」组；关闭时回到「仅第三句包」旧口径 |

> 回归：`test/rain.test.js`（第三句触发/第四句不包/暗杠位移/逐轮陪包/雨主没胡不算/全求人豁免）。

### 吃 / 碰之后必须打牌，不能胡（老吴 2026-09-30）

老吴上报：「本来不够胡，当吃了一句以后，出来一个『自摸』的按钮，可以胡牌了。」

- **根因**：吃/碰之后手里正好 **14 张**（11 张手牌 + 3 张副露），`canWinWith(自摸)` 判定成立 →
  `legalActions` 给出了 `win`。吃/碰凑到的那一番把番数顶过了门槛，于是"突然能胡了"。
- **真实规则**：**吃 / 碰之后必须打出一张，不许胡**。只有**杠后补摸**才许胡 —— 那是「杠上开花」。
- **实现**：`state.mustDiscard`（`doChi` / `doPeng` 置 `true`；`drawTile` 与 `doDiscard` 清 `false`）。
  `legalActions` 的 `discard` 分支据此不给 `win` / `pass`；`doPass` 也会抛「刚吃/碰过，必须先打出一张牌」。
  杠后补摸走的是 `drawTile`，锁自然解开 → **杠上开花照旧**。
- 顺带：**按钮一律叫「胡」**，不再有「自摸」这个按钮名（老吴：不需要）。是不是自摸由引擎判定、
  在结算里体现。

### 听牌提示（老吴 2026-09-30 第 3 条，`src/engine/tenpai.js`）

点右上角「胡牌提示 N」按钮 → 弹出可胡的牌 + **剩余张数** + 「自摸 / 点炮 / 仅自摸 / 仅点炮」。

| 形态 | 触发条件 | 面板内容 |
|---|---|---|
| `wait` | 手牌 = `handNeeded − 1`（真的差一张） | 直接平铺每张可胡的牌 |
| `ready` | 手牌 = `handNeeded`（**轮到你出牌的常态**） | 按「**打 X → 听 N 张**」分组 |

- **剩余张数 = `4 − 明牌张数`**：明牌 = 全局弃牌流水 `discardLog` + 四家副露 tiles + 自己手牌 + `flipTile`。
  别家手牌是暗牌 → 面板说的是「**最多**还剩几张」。
- 候选牌一律过一遍 `canWinWith`（**与真正胡牌走同一套闸门**：开口、门槛、皮子/红中留手、癞子上限…），
  所以「提示能胡的牌」拿到手时引擎确实判胡 —— 这条不变量有专门的测试守着。
- ❗**踩过的最大的坑：只做 `wait` 会得到一个永远不出现的按钮。** 轮到你的时候手里永远是满的
  （刚摸完一张 / 刚吃碰完），压根不存在 `handNeeded − 1` 的状态。
  实测：只做 `wait` 时，种子 1..40 在**真前端**里一次都没亮过；补上 `ready` 后，
  headless 扫 600 局有 **61** 个种子人类能听牌（旧口径只有 14 个）。
  已验证种子：**`GAME_SEED=18`**（`ready` 态，真前端点开过）；与「有胡 → 过」同时覆盖见 `GAME_SEED=355`。
- `tools/verify-ui.mjs` 会点开面板并断言：每张牌都带「剩 N 张」、剩余张数落在 **1..4**、关闭能关掉；
  `tools/viewport-check.mjs` 额外有一个**听牌弹窗档**（换种子重开直到按钮亮起，再量一次溢出）。

### 可胡可过（老吴 2026-09-30 立规矩，2026-10-02 补掉抢杠这个特例，`canPassWin` 默认 `true`）

**有胡时必须允许「过」不胡 —— 自摸 / 点炮 / 抢杠，三种来路一律如此，没有例外。**

| 场景 | 「过」可用？ | 机制 |
|---|---|---|
| **自摸**（轮到自己摸牌后手牌成型） | **可过** | `discard` 阶段 `legalActions` **同时**给出 `win` 与 `pass`；`doPass` 置 `state.winDeclined = true`、记一条「过（不胡）」，**不换手**，玩家继续正常出牌 |
| **点炮**（别人打出的牌能胡） | **可过** | `claim` 阶段 `legalActions` 在 `win` 旁**追加** `pass`；过掉后询问权顺延给下一家（一炮单响） |
| **抢杠胡**（别人蓄杠、你能胡那张） | **可过** | ❗**2026-10-02 改口**。蓄杠时先把响应机会给出去（`state.pendingXuGang = {seat, tile}`，进 `claim` 阶段），给「胡 / 过」；点了「胡」才结算（被抢者**承包**），全「过」才真的补杠（`completeXuGang`） |

#### 为什么抢杠胡以前"不能过"、又是怎么改的（老吴 2026-10-02 报的缺陷）

- **旧设计**：抢杠在 `doXuGang` 里**当场判定并结算**，压根不进 `claim` 阶段 —— 于是「结构上没有『过』的机会」。
- **老吴原话**：「当玩家可以抢杠胡时，直接到了胡牌结算界面，还是应该让玩家点胡以后再结算，但是这个界面没有过的按钮」。
  一句话点中要害：**没机会点「胡」** 和 **没有「过」按钮** 这两个症状，根子是同一个设计决定。
- **现在**：`doXuGang` 只做「**发现有人能抢 → 挂起这次杠 → 进响应阶段**」；真正的补杠挪到 `completeXuGang`。
  `doWin` / `doPass` 按 `state.pendingXuGang` 分支（点炮走 `lastDiscard`、抢杠走 `pendingXuGang`）。
  于是 `legalActions` 那条「**凡给出『胡』必同时给出『过』**」的不变量**对三种来路全部成立，不再有特例**。
- ⚠️ 抢杠阶段 `state.lastDiscard` / `state.lastDraw` 都显式置 `null`：这一手既没有「刚打出的牌」，
  也不能把补杠者刚摸的那张当成抢杠者的 `lastDraw` 下发（既脏又泄牌）。
- ⚠️ 前端提示文案随之分叉（`frontend/render.js`）：`v.pendingXuGang` 存在时提示条写
  「🀄 **抢杠胡！**（南 蓄杠 三筒）　点红色「胡」收分」并加一道金边（`.win-prompt-qg`，红色仍是「胡」，
  金边只是标出这是**承包独付**的最重一种）；提示语是「可以『抢杠胡』，或点『过』让他继续补杠」。
  抢杠**不再**退化成含糊的「可以胡牌！」。

- 自摸「过」掉后：**下次摸牌自动重置**（`drawTile` 里 `state.winDeclined = false`），所以新摸一张若又成型，会重新给「胡 / 过」。
- 把 `canPassWin` 置 `false` 可退回旧行为（有胡必须胡）：`claim` 阶段只给 `win` 不给 `pass`
  （**抢杠同样不给「过」**）；自摸阶段点 `pass` 会被拒 → 抛「本房间口径不允许过胡」。

### 番数与算分：分段计分表（武汉红中赖子杠标准口径）

**番 = 「翻一倍」**。**每家输分按「该家自身番数 + 赢家总番」查表**（不是只看赢家的番），封顶 / 金顶另算。

| 档 | 底番 | 条件 |
|---|---|---|
| 小胡（屁胡） | **0** | 2/5/8 作将，手里最多 1 张癞子。**没有牌型底番**（2026-09-30 老吴修正：原来凭空 +1 番），全靠下面的附加番顶到 6 番门槛 |
| 大胡 | **3 + (种类数 - 1)** | 可累计：第一种大胡 3 番，之后每多一种只 +1 番 |

大胡五种牌型：**碰碰胡 / 清一色 / 将一色 / 风一色 / 全求人**；
三种情境：**杠上开花 / 海底捞 / 抢杠胡**。同一手牌可以叠（例：碰碰胡 + 清一色 = 4 番底，再加将一色 = 5 番底）。
> 该叠加口径对**全部大胡牌型与情境**生效，不是只限示例里的组合；旧口径「种类数 × 3」已废弃
> （把 `fan.bigHuExtra` 设为 3 可退回旧口径做对照）。
>
> ⚠️ **海底捞 / 杠上开花不算「自摸」那一番**（老吴 2026-10-23）：这两种大胡本身由自摸产生，
> 计番时跳过 `selfDraw`；其它大胡自摸仍照加 1 番。开关 `fan.specialBigHuNoSelfDrawFan`（默认 `true`）。

> ✅ **「杠上开花」六种杠都算**（2026-10-22 老吴明确：不管什么杠，只要杠到的牌满足胡牌条件就是杠上开花）：
> **杠 / 蓄杠 / 暗杠 / 红中杠 / 皮子杠 / 癞子杠** 杠后补摸成形都算。
> 特殊杠仍然**不占面子、不算开口**，这是两套独立口径。**普通摸牌绝不会被误标**（`nextDraw` 会清掉杠标记）。
> （注：2026-10-21 修正：**红中杠/皮子杠/癞子杠不算开口**（`specialGangCountsAsOpen:false`），不能凭它们获得胡牌资格；
> 但它们可以免「被阳光」翻倍，暗杠不能免。与「是不是杠上开花」无关。）

番底：庄家 1、自摸 1、放冲 1、硬胡 1、**吃/碰每口 1**；
杠：杠 / 蓄 / 暗 / 癞子杠各 **2**，红中杠 / 皮子杠各 **1**。

> **原赖 / 风赖不加番**（2026-09-30 老吴修正）—— 它们改为把**该局结算的「分数」×2**
> （`yuanLaiMul` / `fengLaiMul`），**两者同时命中仍只 ×2 一次**；**大小胡都翻**。
> 番数里完全不含它们，起胡门槛也只认番数。
> **单笔上限跟着倍率一起翻**（`scaledPayCap`）→ 见下方「封顶」一节。

> 赢家总番 = **牌型底番**（小胡 0 / 大胡 3 + 每多一种 +1）＋ 上面这些**附加番**。
> **结算弹窗**会把每一家的牌 + 各条番数摊开显示；想看完整推导（含「自家X＋赢家Y＝查表Z番」）
> 用 `node tools/simulate.js`。

**分段计分表**（`scoring: 'table'`，默认）：**（该家自身番 + 赢家总番）→ 该家应付分**；超出顶档封顶。

> 例：赢家 6 番，三家自身番 6 / 3 / 5 → 各家查表番数 12 / 9 / 11 番 → 分别付 8 / 5 / 8 分。
> （百度百科·武汉麻将·结算规则·番底：输方要输的分 = 2^(输家所有番数 + 赢家所有番数)）

| 小胡（自家+赢家）总番 | 6 | 7 | 8 | 9 | ≥10 |
|---|---|---|---|---|---|
| 每家分 | 1 | 2 | 3 | 5 | 8（封顶） |

| 大胡（自家+赢家）总番 | 3 | 4 | 5 | 6 | ≥7 |
|---|---|---|---|---|---|
| 每家分 | 1 | 2 | 3 | 5 | 8（封顶） |

> ⚠️ **这是老吴 2026-09-30 拍板的「原文刻度」**。扣掉「小胡底番 1 + 风赖 1 番」那两番后，
> 400 局实测（同一批种子）：**整体金顶率 60.9%**，其中**小胡 30.2%**、**大胡 99.4%**。
> 也就是说：**大胡才是当前金顶率的主要来源** —— 大胡表顶档只有 7 番，而大胡底就 3 番起，
> 加自摸/开口/杠轻松越顶。上移刻度只改 `scoreTable`、引擎一行不改：
> · 只把大胡顶档 7 → 15：整体 60.9% → **28.8%**
> · 大小胡刻度一起上移：整体 → **11.4%**
> **老吴 2026-09-30 拍板「不变」—— 保持原文刻度、接受 60.9%。**
> 📌 该 60.9% 采集于 2026-09-30 旧口径（当时特殊杠不算杠上开花）；
> 2026-10-22 已按老吴纠正改回「六种杠都算」，58.7% 仅为旧口径历史数据，不再代表当前规则。刻度结论与开关结论均不变。

- **封顶（单笔）**：查表每段每家最高 `capScore = 8` 分（查表番数 ≥ 顶档即该家封顶）。
- **金顶（武汉真实口径）**：**三家全部封顶**，**或风一色（全字牌）** → 每家付**自己那份单笔上限**。
  ❗**金顶不再是固定 10 分**（老吴 2026-09-30 二次纠正）：「风赖显示金顶了，可是每家只付 10 分，
  应该是每家 20 分」—— 金顶要**跟着赖 / 未开口一起翻**（见下方公式）。
- **未开口（门清）输家翻倍**：未开口的输家付 `查表分 × 2`。
- **单笔上限跟着倍率走**（老吴 2026-09-30，`scaledPayCap` 默认 `true`）：

  ```
  该家的单笔封顶 = goldScore(10) × mul(赖倍数) × (未开口 ? 2 : 1)
               → 普通 10 ／ 未开口 20 ／ 原赖·风赖 20 ／ 原赖·风赖 + 未开口 40
  ```

  > ❗**金顶与普通局走同一条公式**：非金顶局这道封顶是「夹住过高的一笔」，
  > 金顶局则是「该家应付 = 自己的上限」—— 于是**风赖金顶 = 每家 20 分**（不再固定 10）。
  > ⚠️ **非金顶局的这道封顶在当前「原文刻度」下永远不会被触发**：查表顶档只有 8 分，所以单笔**自然上限**
  > 是 `8×2 = 16`（有赖）与 `8×2×2 = 32`（有赖 + 未开口）—— 都够不到 20 / 40，
  > 于是现状 = **照乘、不封顶**（实际付 16 / 32）。留着这个公式是为了**将来改刻度时封顶自动跟着走**，
  > 同时**让金顶诚实反映倍率**。「非金顶反而比金顶拿得多」的怪相已消失。
  > `node tools/cap-compare.js --rounds 400` 会把「原文刻度」与「顶档抬到 20（非金顶封顶才咬住）」两组摆在一起，
  > 并用 `payments[].payCapApplied` 证明**非金顶封顶在原文刻度下削了 0 笔**。
  > 要退回旧行为（金顶固定 10、非金顶完全不封顶）把 `scaledPayCap` 置 `false` 即可。
- 刻度按 600 局模拟的输家「自家+赢家」番数分布标定 → **单家封顶 ≈ 28%、金顶 ≈ 10%**（见 `tools/simulate.js`）。
- 旧版 2 的幂次方制（`power2`：单笔 = 2^(赢家番+输家番)）与番数相乘（`simple`）作为对照实验保留，默认不再使用。

> ✅ **已结案（老吴 2026-09-30）**：曾出现的「非金顶局单笔 16 分 > 金顶局单笔 10 分」怪相，
> 已由老吴口径「**金顶也跟着翻**」修掉 —— 金顶现在 = 每家自己的单笔上限（风赖金顶 = 20）。

> **风一色 / 字一色口径（2026-10-01 纠正）**：本引擎 `isFengYiSe` 仍判定为"全字牌"（含中发白）。
> 但老吴明确**全字牌（风一色）可以接冲、点炮也能胡** —— 旧「全字牌必须自摸」闸门 `ziYiSeMustSelfDraw` 已删。
> ⚠️ **见字胡 ≠ 全字牌**：见字胡是另一回事（进张靠癞子顶上去），**只有见字胡才必须自摸**，
> 且见字胡只挡点炮、不挡抢杠。若日后要"仅风牌（东南西北，不含中发白）才算风一色"，再另拆风牌专用判定。
> **清（将）一色包牌**：老吴 2026-09-30 口径是「**一色里只有风一色不包，清/将都要包**」→
> `qingJiangBaoEnabled: true`（Rule5-1「第三句」包牌，包家取**副露里第 3 个「可见」该色面子的 `from`**，
> **不是放炮者**；可见 = 吃/碰/明杠/蓄杠，**暗杠与特殊杠不占位** —— 老吴 2026-10-29）。
> 更早的「风清都不包牌」口径已废，仅留 `qingYiSeBaoEnabled: false` 作历史对照。

**硬胡 / 软胡**：硬胡 = 没用癞子凑牌，**或者癞子就当它自己原牌用**（癞子还原）。后者靠额外做一次
「把癞子还原成普通牌再判一次」实现，否则会被误判成软胡。

**承包（包胡）**：抢杠胡时被抢的那家独付全部输分。

### 大胡不算庄家番（老吴 2026-10-03 拍板，2026-10-22 补充）

> 原话：「**大胡的时候不算庄家的额外番**」+「**金顶不算大胡，只是三家都允许，
> 所以金顶可以是大胡，也可以小胡（武汉叫屁胡）**」。
> 2026-10-22 补充：「**大胡的时候，庄家的加倍番，输赢都不算。**」

| 情形 | 庄家番（+1） |
|---|---|
| **小胡**（武汉叫屁胡），赢家是庄 / 赢家是闲 | **照算** |
| **大胡**（含金顶），赢家是庄 / 赢家是闲 / 庄家是输家 | **不算**（全免，不再回补） |

配置项：`bigHuNoDealerFan`，默认 `true`；置 `false` 即回到旧口径（当反向对照用）。

**⚠️ 连带影响：付分档位会降，金顶也可能翻掉**
去掉庄家番 → 输家 `effFan` 下降 → 可能**跌出顶档**。实测一个非金顶大胡用例：

| | 旧口径（算庄家番） | 新口径（大胡免） |
|---|---|---|
| 输家番 `fan` | 1 | **0** |
| 输家计分番 `effFan` | 6 | **5** |
| 每家付分 `pay` | 5（6 番档） | **3**（5 番档） |
| 赢家总收入 | 15 | **9** |

（大胡表 `[[3,1],[4,2],[5,3],[6,5],[7,8]]` —— 5 番档是 3 分。）

如果某家原本靠这 1 番才够顶档，大胡免庄家番后会**不再是金顶**；这是规则本身的直接结果，
引擎**不做回补**。金顶判定仍按 `effFan = 赢家番 + 输家番（不含庄家番）` 计算。

  奖金在**本局正常结束时**（胡牌或荒庄）结算，作为与胜负独立的附加账本（`result.bonuses` / `result.bonusTotal`）。
- **分别计算**：七皮和十杠若同时达成，是**两笔独立奖金**（各自从三家各收 `goldScore`），互不抵消。
- **七皮计数** = 副露中属于 `skinTiles` 的张数（`countSkinsGanged`）——**不含手牌、不含只摸到过的**；
- **十杠计数** = 副露中六类杠的条数（`countGangUnits`），吃/碰不计口；
- 这两项是房主建房时可开关的规则（`RULE_HINTS` 已留 UI 旋钮位）。

> **七皮口径（2026-10-08 最终拍板，覆盖前两版）**
> 原话：「**七皮是指杠出来的牌里面，红中和皮加起来有 7 个**」
> —— 只数**已经进入副露的**皮子/红中，判定函数 `countSkinsGanged(melds, skinTiles)`。
>
> | 口径 | 3000 局达成率 |
> |---|---:|
> | v1 手牌+副露同时持有 7 张 | 0.05% |
> | v2 累计经手（摸到+杠走，`countSkinsSeen`） | 13.48% |
> | **v3 最终：只数杠出来的**（`countSkinsGanged`） | **0%（12000 个局×家一次未成）** |
>
> 明确**不计入**的三类：① 手牌里仍留着的皮子；② 只是摸到过、没杠走的皮子；
> ③ **癞子杠的癞子本身**（`wildTile` 是独立字段，**不在 `skinTiles` 里**）。
> 实际能贡献的只有 **皮子杠（每次 1 张）+ 红中杠（每次 1 张）** ——
> 冲杠/暗杠虽然副露 4 张，但皮子不能被碰/暗杠（`canClaimSpecialTiles:false` + `specialTilesNoAnGang:true`），实测贡献 **0**。
> ⇒ 一家要连做 7 次皮子杠或红中杠。**门槛是否下调待老吴确认。**

> **十杠口径（2026-10-03 23:38 定，2026-10-08 二次确认 + 三次补正）**
> 原话：「**10 杠是指杠牌（包括红中杠、皮子杠、赖子杠、冲杠、蓄杠）的杠数加起来达到 10**」
> + 「**暗杠/癞子杠 2 口是对的啊，不是错误实现**」
> + 「**蓄杠的口数，碰算 1 口，杠算 1 口，合计 2 口**」—— 加权口数，配置在 `shiGangWeights`：
>
> | 杠 | 冲杠 `zhi` | **蓄杠 `xu`** | **暗杠 `an`** | 红中杠 `red` | 皮子杠 `skin` | **癞子杠 `wild`** |
> |---|---|---|---|---|---|---|
> | 口数 | 1 | **2** | **2** | 1 | 1 | **2** |
>
> **为什么蓄杠是 2 口**：蓄杠 = 先「碰」一手（1 口）+ 再「杠」一手（1 口）。
> 引擎里蓄杠是把已有 `peng` 副露**原地改写**成 `xu`（`completeXuGang`：`meld.type = 'xu'`），
> `melds` 数组里**只有一条**、补摸那手也在 `afterGangDraw` ⇒ 数副露条数只能得 1，
> 必须靠 `shiGangWeights.xu = 2` 表达。测试里有专门一条盯着这个。
>
> 3000 局 / 12000 个「局×家」实测演进：
>
> | 口径 | 单家平均杠口 | 十杠达成率 |
> |---|---:|---:|
> | 六种一律 1 口 | 2.12 口 | 1/12000 = 0.0083% |
> | an/wild = 2 | 2.71 口 | 34/12000 = 0.2833% |
> | **an/wild/xu = 2（定稿）** | **2.78 口** | **46/12000 = 0.3833%** |
>
> 各杠对总杠口的贡献（加权后）：癞子杠 13202 口 > 皮子杠 9962 > 红中杠 6260 >
> 蓄杠 1668（834 次 ×2）> 冲杠 1458 > 暗杠 766。单家 ≥7 口占 2.3%，≥10 口 46 个「局×家」，最高 13 口。
>
> ⚠️ 曾一度误解成「六种一律 1 口」并把 an/wild 撤成 1，**这是错的**，已按老吴二次确认改回 2。
>
> ⚠️ **别跟「杠的番底」搞混** —— 那是**两套独立配置**（数值恰好一致，但改一个不影响另一个）：
> - `gangFan`（数**番**，老吴 10-08 定稿）：**冲杠 2 番、蓄杠 2 番（碰1+杠1）**，暗杠/癞子杠各 **2 番**，红中杠/皮子杠各 **1 番**
> - `shiGangWeights`（数**口**，用于十杠成就）：蓄杠/暗杠/癞子杠各 **2 口**，其余各 **1 口**

## v0.2 纠正了什么

v0.1 实现的是「112 张 + 红中当万能牌」，与真实武汉红中赖子杠有 8 处结构性差异：

| # | 项 | v0.1（错） | v0.2（对） |
|---|---|---|---|
| 1 | 用牌 | 112 张，无风牌 | **136 张**，含东南西北中发白 |
| 2 | 万能牌怎么来 | 红中固定是万能的 | **开局翻底牌动态决定** |
| 3 | 皮子 | 没有这个概念 | 癞子往回数 2 张 + 红中（3 种 11 张），留手不能胡 |
| 4 | 红中的角色 | 万能牌 | **固定杠牌**，留手不能胡 |
| 5 | 小胡将牌 | 任意对子 | **必须 2/5/8** |
| 6 | 七对 | 允许 | **没有七对** |
| 7 | 暗杠算开口 | 算 | **不算** |
| 8 | 算分 | 番数相加制 | **分段计分表**：每家按「自家番 + 赢家番」查表，含封顶 / 金顶（**金顶随赖·未开口倍率翻**） |

### 三家暗牌「真 3D 侧立」（老吴 2026-10-03 参照图）

参考图里三家（对家 / 左家 / 右家）的暗牌是**立起来的牌墙**，不是平铺的牌背。已用
`perspective` + `rotate` 做出真 3D，**且高度一个像素都没动**。

| 家 | transform | 说明 |
|---|---|---|
| 对家（上） | `scaleY(2.6) scaleX(1.15) rotateX(28deg)` | 俯视，看得到牌面 |
| 左家 | `scaleX(0.62) scaleY(2.4) rotateY(28deg)` | 侧立朝桌心 |
| 右家 | `scaleX(0.62) scaleY(2.4) rotateY(-28deg)` | 镜像 |

`perspective: 420px; perspective-origin: 50% 42%` 挂在 **`.hand-backs`（三家共同祖先）**。

#### 为什么做 3D 却没破高度固定 —— 本段最关键的约束

**一律用 `transform`，绝不改 `height` / `width` / `margin` / `padding`。**
`transform` 是**绘制层**变换、不参与布局计算：盒子占位仍是原来的 22px/18px，
所以「整页高 / 牌桌高 / 座位下沿 / 手牌下沿」四个硬指标必然零漂移。
（改 `height` 就正好踩中老吴 2026-10-01 花一天在修的那个坑。）

实测确认：4 档视口的高度数字与加 3D 之前**逐项完全一致**
（`860/783/840/831`、`860/774/836/827`、`390/356/386/382`、`375/341/371/367`）。

> ✅ 附带好处：`perspective` 挂在共同祖先时，`getBoundingClientRect()` 返回的是**未变换**的布局框
> ⇒ `viewport-check` 的高度断言天然不受影响，**一行工具都不用改**。
> ⚠️ 但如果把 `perspective` / `transform` 挂到 `.hand-backs` 自身，rect 就会包含变换 ⇒ 工具误报漂移。别这么改。

#### 调参时翻过两次车（数值都是实测反解出来的，不是拍脑袋）

1. **`rotateY(58°)` → 牌变成 2~3px 的竖直细线**，完全读不出「立着的牌」是什么。
   18px 宽的牌压得太狠 ⇒ 降到 30° 左右才保住 8~10px 可辨识宽度。
2. **`scaleX(1.9)`（本想把牌「加厚」）→ 相邻牌互相重叠、糊成一条绿棍。**
   根因是**牌本来就故意重叠**：实测侧家 `pitch 10.9px < 牌宽 16.3px`（重叠 0.669 倍），
   对家 `pitch 12.5 / 牌宽 10.6 = 1.18`。⇒ **放大倍数必须按 `pitch / 牌宽` 反解**：
   `scaleX ≤ 1.18`（对家）/ `< 0.67`（侧家）才安全，**侧家只能缩不能放**。
3. **纵向（`scaleY`）可以大幅放大**，因为排布是横向的、纵向不参与粘连；
   且横屏侧栏实测 186px 高而牌只占 25px ⇒ 纵向大量空闲，这正是「矮墙」观感的来源。

#### 一条不能碰的例外

**自己的手牌（`.seat-bottom`）绝不能进 3D** —— 牌面文字一转就读不清，
而且双击出牌的命中区域会跟着偏。三家能转是因为它们只显示牌背、不露牌面。

### 2026-10-03 两条口径纠正

| # | 项 | 旧 | 新（老吴拍板） |
|---|---|---|---|
| 1 | **大胡的庄家番** | 大胡照算庄家 +1 | **大胡不算**（`bigHuNoDealerFan`，默认 `true`）。小胡照算；大胡**输赢都不算**，**金顶也不回补**。详见「大胡不算庄家番」一节 |
| 2 | **杠的叫法** | 按钮/文案叫「冲杠」 | 一律叫「**杠**」—— 武汉没有「冲杠」这个说法。**只改显示文案**，`zhi` / `gangZhi` 等内部标识一律不动 |
| 3 | **七皮 / 十杠的奖金** | 固定 10 分/家，**不跟赖子倍率** | **只有本局是风赖、或是原赖时才 ×2**（20 分/家），其余一律 10 分 ——「风赖、原赖要翻番（包括七皮、十杠如果发生在风赖、原赖，也乘以二）」。判据只看本局是不是风赖/原赖（与谁胡牌无关，荒庄局同样算） |

> 第 1 条的实现关键是：金顶判定依赖 `effFan`，而大胡免庄家番会降低 `effFan`。
> 2026-10-22 起口径改为**大胡一律免、金顶不回补**，因此少 1 番导致的金顶翻转就是最终结果。
> 另有一处**隐藏 bug 顺手修掉**：`settleRound` / `settleRoundTable` 以前**漏传 `size`**，
> 导致 `size` 恒为 `null` —— 这条新规则要靠 `size === 'big'` 判断，不修就等于规则完全不生效。

## 部署（NAS / Linux）

网络对战服务（Fastify + Socket.IO + SQLite）支持 **Docker** 与 **裸机** 两种落地方式，
群晖 / 威联通 / 反向代理 / 备份升级的完整步骤见 **[docs/deploy.md](docs/deploy.md)**。

**Docker** —— Linux 服务器，或群晖 Container Manager / 威联通 Container Station

```bash
cp .env.example .env          # 至少把 JWT_SECRET 换成 `openssl rand -hex 32` 的结果
docker compose up -d --build
```

**裸机 Linux**（有 systemd 的常规发行版；NAS 没有 systemd，请用上面 Docker）

```bash
sudo deploy/install.sh        # 校验 Node>=20 → 同步到 /opt/mahjon → 装依赖 → 装 systemd → 自检 /health
```

两者数据都固定落**数据目录**（Docker 是挂载卷 `/data`，裸机是 `/var/lib/mahjon`），
3000 端口对外提供：`/`（验证台）、`/app`（单机牌桌）、`/app/net`（网络对战大厅 + 牌桌）、
`/health`、`/api/*`、`/play`（Socket.IO）。

> Node 22 启动需带 `--experimental-sqlite`（`npm start`、Dockerfile、systemd 单元均已带），Node 24+ 可省。
> 走域名 + 反向代理时，`/play` 必须转发 WebSocket 升级头，否则能登录但一进牌桌就断连。

## 设计要点

**1. 服务端权威 + 纯函数状态机**
所有牌局事实只存在于 `state`，客户端只发「意图」。`act(state, action)` 原地推进，
零 I/O、零 `Math.random`，同一 seed 可完整复算 —— 排查争议牌靠这个。

**2. 别人的手牌永不下发**
`viewFor(state, seat)` 只输出该玩家可见的信息，其他家仅暴露张数，从根上杜绝看牌。

**3. 面子折算的两个坑（都已处理）**
- 手牌张数 = `14 - 3 × 副露数`（等待摸牌时是 `13 - 3 × 副露数`）
- **红中杠/皮子杠/癞子杠只占 1 张牌，不折算面子** —— 拿 `melds.length` 去算手牌张数，
  会把杠过红中的玩家误判成张数不符，永远胡不了。这类杠统一走 `exposedMeldCount()`

**4. 癞子对算法完全透明**
`win.js` 不知道「哪张是癞子」，癞子由参数传入。红中**永远**是皮子、绝不可能是癞子
（见 `game.deriveWild` 的硬保证：字牌按「东南西北 红中 发财 白板」推进但**跳过红中**，
翻北 / 翻红中时癞子都顺延为发财）。旧的 `wildMode='redDragon'`（红中当癞子）变体已废弃。

**6. 响应等待时间是房间级配置参数**
防卡死靠 `ruleset.claimTimeoutMs`（默认 8000ms，房主建房时可覆盖）：他人打牌后，
可吃/碰/杠/胡的玩家必须在这么多毫秒内给动作，超时由服务端自动代其 `pass`。
`createRuleSet` 会对它做校验——非正数/NaN 回退默认 8000，小数四舍五入，
避免误填 0 导致瞬间跳过或填错导致永不超时。`RULE_HINTS` 里「响应等待」一项即给它留的 UI 旋钮位。

> ⚠️ 它**只管响应阶段**。「轮到某人出牌时他掉线了」这类死锁要另靠
> `offlineAbsentMul` / `offlineDissolveMul`（托管 / 判离席），见上文「长断线：托管」。

> 单机版前端（2026-10-01 补）：原本只留了服务端字段、前端没驱动，故「8 秒不响应自动过」一直没生效。
> 现已在前端实现——轮到人类响应且存在「过」动作（claim 阶段 / 自摸可过）时启动 `claimTimeoutMs` 倒计时，
> 超时自动 `pass`，底部 `#auto-pass-tip` 显示「⏱ N 秒后自动「过」」。纯出牌阶段（必须出牌、无过）不动。
> 调试可用 `frontend/build/index.html?timeout=600` 把超时压短。`tools/verify-auto-pass.mjs` 专门验证它。

**5. 胡牌判定返回「全部拆解」而非布尔值**
同一手牌可能既能拆碰碰胡又能拆平胡，算番要挑番高的那版。
拆解打平时优先选癞子用得少的方案，更贴近实际打法直觉。

**7. 原赖 / 风赖 + 七皮 / 十杠（新一轮、跨回合状态）**
- 这两类规则要"记住上一局"或"跨整个回合累计"，所以状态分成两个层次：
  - **跨局**：`prevWildTile` 由建房/开新一轮时从上一局 `wildTile` 传入，
    引擎据此算 `yuanLai`（原赖），**不进 `state` 的 RNG/比较逻辑**，因此不影响 seed 复算。
  - **跨动作（回合内累计）**：`七皮 / 十杠` 用 `refreshAchievements(state)` 在每次 `act()` 后刷新，
    标记 `qiPi` / `shiGang` 是 **sticky**（达到即锁，之后弃牌也不丢）。
- 奖金走**独立账本**（`computeSpecialBonuses`），与 `settleRound` 的胜负矩阵解耦：
  荒庄（`settleDraw`）和胡牌（`finishWin`）两条终局路径都调用它，
  达成者从其余三家各收 `goldCap`，七皮与十杠同时达成则两笔独立相加。

**8. 抢杠胡复用响应阶段（`pendingXuGang`），不另开一条路径**
`claim` 阶段本来就是「把散装选项按优先级 + 座位距离排队、逐个问」的那套机器。
抢杠要的东西和点炮**完全一样**（给「胡 / 过」，点了「胡」才结算），所以正确做法是**复用**，而不是特判：
- `beginClaims` 里把「聚合 + 排序 + 切阶段」抽成 `enterClaimPhase(state, options, fromSeat)`；
  点炮与抢杠共用它，于是「一炮单响按下家优先」在抢杠场景自动成立。
- `doXuGang` 只负责**发现有人能抢 → 挂起这次杠**（`state.pendingXuGang = {seat, tile}`）→ 进响应阶段；
  **真正补杠挪到 `completeXuGang`**，由「全『过』」或「本来没人能抢」两条路调用。
- `doWin` / `doPass` 按 `pendingXuGang` 是不是 `null` 分支（进张 = 被加杠的那张 vs 刚打出的那张；
  承包者 = 补杠者 vs 放炮者）。`finishWin` / `settleDraw` 都把它清掉，终局不留脏值。
- 好处：`legalActions` 里那条「**凡给出『胡』必同时给出『过』**」的不变量
  **对自摸 / 点炮 / 抢杠一律成立**，不再需要「抢杠是特例」的注解 —— 少一个特例，少一处会腐坏的地方。
- ⚠️ 每个待抢的选项各自带着**自己的** `ctx`（`from: 补杠者`、`qiangGangHu: true`）。
  `doWin` 靠 `state.pendingXuGang` 是不是 `null` 区分「抢杠 / 点炮」，不靠座位号 ——
  所以「一家『过』→ 轮到下一家」时，下一家那份 ctx 依然正确（`test/game.test.js`
  的「两家都能抢时，下家先问」覆盖了队列推进与漏抢后仍可胡）。

| 配置 | 胡牌率 | 荒庄率 | 大胡占比 | 硬胡占比 | 门清胡占比 | 平均步数 |
|---|---|---|---|---|---|---|

| **N 番起胡（口口 6 番）** | 92.0% | 8.0% | **53.3%** | 60.9% | 0% | 77.4 |

逐条解读：

- **开口番 vs 口口番**：牌局过程完全一致（同一批种子），只有番数不同 ——
  口口番赢家平均 10.02 番 vs 开口番 8.63 番，金顶+光明顶 127 次 vs 95 次。**开关生效 ✓**
- **关掉必须开口**：门清胡从 0% 升到 5.9%，平均步数 70.1 → 68.1。**开关生效 ✓**
- **关掉癞子**：硬胡占比从 54.5% 变 100%（没有癞子自然全是硬胡），
  平均步数 70.1 → 76.9（少了万能牌，成牌变难）。**开关生效 ✓**
- **N 番起胡**：小胡被门槛滤掉，大胡占比 39.0% → 53.3%，赢家平均番数 10.02 → 12.32。**开关生效 ✓**
- **关掉「红中/皮子留手」两道闸门**：指标**完全不变** —— 因为这套机器人本来就优先把红中/皮子打出去
  （`tileValue` 给 -1000），闸门从未被触发。闸门本身由单测覆盖，不是没生效。
